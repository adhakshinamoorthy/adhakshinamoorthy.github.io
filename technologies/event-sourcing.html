Event Sourcing

Event Sourcing persists the history of what happened to a domain object rather than just its current state, making every change first-class and queryable.

⏱ 38 min readUpdated Aug 7, 2026Level: Advanced

Overview

Instead of storing the current row in a database table, an event-sourced system appends a new immutable event every time something meaningful happens to an aggregate. Current state is derived by replaying those events in order. This gives a complete audit trail for free, enables temporal queries, supports event replay into new projections, and makes debugging production incidents far easier. The trade-offs are query complexity, event versioning discipline, and the need for snapshot strategies when event streams grow long.

What you will learn

  • Treat streams as source of truth.
  • Rehydrate deterministically.
  • Append with expected-version concurrency.
  • Build idempotent projections.
  • Evolve immutable schemas.
  • Operate snapshots, replay, privacy, backup, and recovery.

Prerequisites

  • DDD, CQRS, serialization, and concurrency.
  • Eventual consistency and projections.
  • A concrete historical business need.

When to use Event Sourcing

Good fit

  • History and temporal decisions have value.
  • Replayable projections are required.
  • The domain is behavior-rich.

Choose another approach when

  • Current CRUD state is enough.
  • Privacy requirements are unresolved.
  • Schema evolution and rebuild operations are unavailable.

Key concepts

Event streams

Ordered append-only aggregate facts.

Rehydration

Replay reconstructs state.

Expected version

Optimistic concurrency rejects stale appends.

Uncommitted events

Decisions produce events before persistence.

Projections

Subscribers build query models.

Snapshots

Measured checkpoints reduce replay.

Schema evolution

Upcasters translate history.

Subscriptions

Global positions track projection progress.

Architecture

Commands produce domain events appended to an event store; projections subscribe to the store and populate read models that queries use.

Code example

The aggregate applies events to change its own state; the command handler appends those events to the store rather than saving a mutated entity.

Order.cs
public sealed class Order
{
    public Guid Id { get; private set; }
    public OrderStatus Status { get; private set; }
    public decimal Total { get; private set; }

    public static (Order, IReadOnlyList<object>) Place(
        Guid id, CustomerId customerId, IEnumerable<OrderLine> lines)
    {
        var order = new Order();
        var events = new List<object>
        {
            new OrderPlaced(id, customerId, lines.ToList(), DateTime.UtcNow)
        };
        foreach (var e in events) order.Apply(e);
        return (order, events);
    }

    public (IReadOnlyList<object> Events) Cancel(string reason)
    {
        if (Status != OrderStatus.Pending)
            throw new DomainException("Only pending orders can be cancelled.");

        var events = new List<object> { new OrderCancelled(Id, reason, DateTime.UtcNow) };
        foreach (var e in events) Apply(e);
        return (events);
    }

    private void Apply(object @event)
    {
        switch (@event)
        {
            case OrderPlaced e:
                Id = e.OrderId;
                Status = OrderStatus.Pending;
                Total = e.Lines.Sum(l => l.Subtotal);
                break;
            case OrderCancelled:
                Status = OrderStatus.Cancelled;
                break;
        }
    }

    // Reconstitution: load from event stream
    public static Order Rehydrate(IEnumerable<object> events)
    {
        var order = new Order();
        foreach (var e in events) order.Apply(e);
        return order;
    }
}

public sealed record OrderPlaced(
    Guid OrderId, CustomerId CustomerId,
    IReadOnlyList<OrderLine> Lines, DateTime OccurredAt);

public sealed record OrderCancelled(
    Guid OrderId, string Reason, DateTime OccurredAt);
note

Event sourcing solves the audit and temporal query problem well, but adds complexity around versioning, projection rebuilds, and eventually consistent reads — apply it where that trade-off is genuinely worth making.

Testing strategy

Test decisions and replay separately.

  • Assert events from history.
  • Replay and assert state.
  • Reject stale versions.
  • Replay projections twice.
  • Test upcasters.
  • Rebuild from backup.

Security considerations

Immutable history complicates data lifecycle.

  • Minimize sensitive data.
  • Design encryption keys.
  • Authorize stream access.
  • Protect projections.
  • Audit replay and export.

Performance and scalability

Stream length and projection throughput shape cost.

  • Bound event size.
  • Snapshot from evidence.
  • Batch projection reads.
  • Partition subscriptions.
  • Track lag and replay rate.

Deployment and operations

Events outlive code versions.

  • Deploy upcasters.
  • Use additive evolution.
  • Version projections.
  • Preserve checkpoints.
  • Rehearse restore and rebuild.

Common problems and fixes

Replay state differs.

Likely cause: Apply is nondeterministic.

Fix: Remove time and I/O.

Concurrent writes overwrite.

Likely cause: Expected version is absent.

Fix: Use optimistic append.

Projection duplicates.

Likely cause: Updates are not idempotent.

Fix: Store positions with effects.

Old events fail.

Likely cause: Schema is incompatible.

Fix: Add upcasters.

Load is slow.

Likely cause: Streams are long.

Fix: Measure and snapshot.

Deletion conflicts with history.

Likely cause: Privacy design is missing.

Fix: Minimize and crypto-shred where appropriate.

Best practices

  • Use past-tense facts.
  • Keep streams aggregate-scoped.
  • Append with expected versions.
  • Keep apply pure.
  • Make projections idempotent.
  • Upcast history.
  • Snapshot only from evidence.
  • Rehearse rebuilds.
tip

Use Marten with PostgreSQL as an event store for a pragmatic .NET start — it gives you append-only streams, snapshots, projections, and async subscriptions without running a separate event store infrastructure.

warning

Do not use event sourcing as a default persistence strategy for every aggregate; apply it where auditability, temporal queries, or event replay provide concrete business value that justifies the operational cost.

Production checklist

  • Business value is explicit.
  • Events are immutable facts.
  • Apply is deterministic.
  • Expected-version append is atomic.
  • Projections rebuild idempotently.
  • Evolution is tested.
  • Privacy lifecycle is resolved.
  • Restore and reconciliation are rehearsed.
