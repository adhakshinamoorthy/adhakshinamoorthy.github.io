Background & Hosted Services

Background processing lets an application do meaningful work—emails, media pipelines, cleanup, retries—without blocking a request or depending on a client staying connected.

⏱ 34 min readUpdated Aug 13, 2026Level: Foundation to production

Overview

The .NET Generic Host starts registered IHostedService instances, coordinates BackgroundService execution, propagates cancellation, and gives each service a bounded graceful-shutdown window. In-process workers suit lifecycle-bound loops, polling, telemetry, and best-effort local queues; they do not make accepted work durable. A bounded Channel can separate producers and consumers while applying backpressure, but pending items disappear when the process fails. Durable schedulers, databases, or brokers are required for work that must survive restart, coordinate replicas, run once according to a business schedule, or support operator replay. Hosted services are singletons, so each item creates and disposes its own dependency-injection scope. Production loops avoid overlapping timers, propagate cancellation, isolate item failures, bound retries and concurrency, make effects idempotent, expose progress and oldest-work age, stop admission before drain, and checkpoint unfinished durable work before the shutdown deadline.

Prerequisites

  • Generic Host, DI, async C#, cancellation, and logging.
  • Queue, retry, idempotency, health, and deployment basics.
  • A durability requirement.

When to use Background & Hosted Services

Good fit

  • Work belongs to the app lifecycle.
  • Local work tolerates process loss.
  • A worker consumes a durable queue.

Choose another approach when

  • Requests start fire-and-forget work.
  • Local work must survive restart.
  • Independent scaling needs another deployment.

Key concepts

Host lifecycle

Hosted services participate in startup and shutdown.

BackgroundService

ExecuteAsync owns a cancellable loop.

Bounded queues

Channels create backpressure.

Dependency scopes

Singleton workers create scopes per item.

Periodic work

PeriodicTimer avoids overlap.

Durability

Local queues lose work on crash.

Idempotency

Repeated work must not duplicate effects.

Health and drain

Progress, cancellation, and checkpointing define safe operation.

Architecture

A producer enqueues durable job records; one or more workers claim and process them, writing results back to the same store they were claimed from.

Code example

Register a recurring job alongside its dependencies so scheduling and business logic stay in one discoverable place.

ExportModule.cs
public static class ExportModule
{
    public static IServiceCollection AddExportJobs(this IServiceCollection services)
    {
        services.AddScoped<IReportExporter, ReportExporter>();
        return services;
    }

    public static void MapExportJobs(this IRecurringJobManager jobs)
    {
        jobs.AddOrUpdate<IReportExporter>(
            "nightly-export",
            exporter => exporter.ExportAsync(CancellationToken.None),
            Cron.Daily(hour: 2));
    }
}
note

A hosted service and a durable job scheduler solve different problems: use the former for lightweight in-process loops and the latter when work must survive restarts or run on a schedule.

Testing strategy

Test lifecycle and failure behavior.

  • Test bounded admission.
  • Cancel idle and active work.
  • Isolate item failures.
  • Verify scope disposal.
  • Test drain timeout.
  • Restart durable work idempotently.

Security considerations

Workers execute with service privilege.

  • Use least privilege.
  • Validate tenant and size.
  • Do not capture request credentials.
  • Redact payloads.
  • Protect replay controls.

Performance and scalability

Concurrency matches dependency capacity.

  • Bound queues.
  • Tune consumers.
  • Avoid tight polling.
  • Batch carefully.
  • Track oldest age.

Deployment and operations

Workers stop and resume predictably.

  • Set shutdown grace.
  • Stop readiness before drain.
  • Coordinate singleton schedules.
  • Checkpoint progress.
  • Test backlog recovery.

Common problems and fixes

Worker stops.

Likely cause: Unhandled exception.

Fix: Isolate failures.

Memory grows.

Likely cause: Unbounded queue.

Fix: Bound capacity.

Scoped errors.

Likely cause: A scoped service was captured.

Fix: Create per-item scopes.

Jobs overlap.

Likely cause: Timer reentry.

Fix: Use a sequential loop.

Deploy loses work.

Likely cause: Queue is local.

Fix: Use durable storage.

Shutdown hangs.

Likely cause: Cancellation is ignored.

Fix: Propagate tokens and cap drain.

Best practices

  • Use cancellable loops.
  • Use bounded Channels.
  • Create scopes per item.
  • Use PeriodicTimer.
  • Use durable storage when required.
  • Make effects idempotent.
  • Bound retries.
  • Measure age and shutdown.
tip

Add a dashboard or admin view for scheduled and failed jobs early; debugging background work without visibility is expensive.

warning

Do not rely on in-memory queues or timers for anything that must not be lost on deploy or crash; use a durable store.

Production checklist

  • Durability is explicit.
  • Admission and concurrency are bounded.
  • Cancellation propagates.
  • Scopes are per item.
  • Effects are idempotent.
  • Poison work is isolated.
  • Age and progress alert.
  • Shutdown and recovery are rehearsed.
